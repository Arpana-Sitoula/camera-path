\begin{abstract}

Scientific visualization tools such as Met3D enable meteorologists to examine weather phenomena in three dimensions, but camera control remains largely manual. When multiple tropical cyclones (TCs) and atmospheric rivers (ARs) occur simultaneously, deciding which features to inspect and how the camera should move can be difficult. This work presents the meteorological analysis stage of an automated camera-planning system that converts the output of an existing neural detection pipeline into information for camera planning. Detected features are linked across forecast timesteps using nearest-centroid matching based on geodesic distance and characterized by their lifetime, travel distance, spatial extent, and shape volatility. Shape volatility captures changes in area as well as split and merge interactions. These measures are combined to rank the tracked features and assign one of three camera-motion types: follow, skeleton, or orbit. The resulting tracks and motion assignments are exported to a separate camera-trajectory generation module, which produces camera animations compatible with Met3D.

\end{abstract}



\section{System Overview}

The system consists of four stages arranged as a linear pipeline, with a hand-off from meteorological analysis to cinematographic rendering.

\begin{enumerate}
    \item \textbf{Detection:}
   Global forecast data from the German Weather Service in NetCDF format is processed by the existing CGNet-based segmentation network. For each of the timesteps, the network produces probability fields for background, tropical cyclone (TC), and atmospheric river (AR). This detection component was developed as prior work and is not part of this study.

    \item \textbf{Feature Extraction and Tracking:}
    Each timestep's probability field is thresholded and segmented independently into candidate features, which are then linked across consecutive timesteps into continuous tracks.

    \item \textbf{Feature Ranking and Motion-Type Selection:}
   Each track is characterized using four measures and assigned a relevance score. Based on these characteristics, one of three camera-motion types is selected: follow, skeleton, or orbit.

    \item \textbf{Camera Trajectory Generation and Rendering}
    The ranked, motion-typed tracks produced by stage 3 are converted into Met3D-compatible camera keyframe sequences (Section 2.3), which are then rendered and validated against Met3D's visual output (Section 3).
    
\end{enumerate}

\section{Methodology}

\subsection{Feature Extraction and Tracking}

\textbf{Input representation:} The method operates on a sequence of NetCDF probability fields $P_t(x,y)$, one per forecast timestep $t \in \{1,2,3,\dots\}$, each giving the network's estimated likelihood that location $(x,y)$ belongs to the feature class of interest (TC or AR).

\textbf{Thresholding:} Each probability field is converted to a binary candidate mask by thresholding at $\tau = 0.5$:
\begin{equation}
B_t(x,y) =
\begin{cases}
1, & P_t(x,y) \geq \tau \\
0, & P_t(x,y) < \tau
\end{cases}
\tag{1}
\end{equation}

\textbf{Connected-component filtering:} Connected-component labelling is applied to $B_t$ to identify spatially contiguous candidate features. Components smaller than a class-specific minimum size are discarded to remove noise and isolated detections. The current implementation uses minimum sizes of 50 pixels for TC candidates and 200 pixels for AR candidates, reflecting the different spatial scales of the two feature types.

\textbf{Spatial descriptors:} For each surviving component, a set of geographic descriptors is computed. For tropical cyclones, the descriptor of interest is the centroid, taken as the center of mass of the component's pixels:
\begin{equation}
\mathbf{c} = \frac{1}{n}\sum_{j=1}^{n}(x_j,y_j),
\qquad
(x_j,y_j) \in \Omega
\tag{2}
\end{equation}
where $\Omega$ is the set of pixels belonging to the component.

For atmospheric rivers, no single point is representative, and the component is instead reduced to its skeleton which is a one-pixel-wide centerline obtained via a standard skeletonization algorithm. The skeleton's two endpoints and its midpoint serve as the key waypoints characterizing the river's spatial extent, analogous to finding the backbone of a ribbon-shaped object.

\textbf{Temporal tracking:} Each timestep's set of feature observations $F_t = \{f_1,\dots,f_n\}$ is associated with the observations at $t+1$ using nearest-neighbour matching on the great-circle (Haversine) distance between centroids. For two points at latitude/longitude $(\varphi_1,\lambda_1)$ and $(\varphi_2,\lambda_2)$, expressed in radians:
\begin{equation}
a =
\sin^2\!\left(\frac{\Delta\varphi}{2}\right)
+
\cos\varphi_1\cos\varphi_2
\sin^2\!\left(\frac{\Delta\lambda}{2}\right),
\qquad
d =
2R \cdot
\operatorname{atan2}\!\left(\sqrt{a},\sqrt{1-a}\right)
\tag{3}
\end{equation}
where $R \approx 6371\,\text{km}$ is the Earth's mean radius.A feature at time $t$ is linked to the closest feature at $t+1$ when the distance $d$ is within a predefined maximum radius. This radius is used to allow for the expected movement of a feature between two consecutive forecast hours. If the distance is larger than this radius, the two features are not linked, which helps avoid connecting unrelated detections. 

The resulting associations form a trajectory for each feature $i$:
\begin{equation}
T_i = \{f_{i,t_1}, f_{i,t_2}, \dots, f_{i,t_k}\}
\tag{4}
\end{equation} represents the life cycle of the feature over the timesteps in which it was detected.

\subsection{Feature Ranking}

\textbf{Characterization:} Each completed trajectory $T_i$ is summarized along four metrics intended to capture how relevant the feature is likely to be for visualization.

\textit{Lifetime} is the duration over which the feature could be continuously tracked:
\begin{equation}
L_i = t_k - t_1
\tag{5}
\end{equation}

\textit{Total travel distance} is the cumulative geographic displacement of the feature's centroid over its tracked lifetime, computed as the sum of consecutive Haversine distances (Eq. 3):
\begin{equation}
D_i =
\sum_{j=1}^{k-1}
d\!\left(
\mathbf{c}_{i,t_j},
\mathbf{c}_{i,t_{j+1}}
\right)
\tag{6}
\end{equation}

\textit{Spatial extent} $E_i$ describes the geographic size of the feature, derived from the spatial dimensions (e.g., bounding-box diagonal or mask area) of the detected component, averaged or maximized over the track.

\textbf{Shape volatility.} $V_i$ combines two signals: how much the
feature's area changes frame-to-frame, and how often it has a nearby
same-class neighbour. In plain terms: for every timestep the track was
observed, the procedure checks whether any other detected blob of the same
feature class lies within a radius $r_{sm}$; if one does, that timestep is
counted as one split/merge interaction. The two signals are the mean
frame-to-frame change in pixel area,
\begin{equation}
\overline{\Delta A}_i =
\frac{1}{k-1}
\sum_{j=1}^{k-1}
\left| a_{i,t_{j+1}} - a_{i,t_j} \right|
\tag{8a}
\end{equation}
and the count of timesteps with at least one nearby same-class neighbour,
\begin{equation}
n_i^{\mathrm{sm}} = \sum_{j=1}^{k} \delta_j,
\qquad
\delta_j =
\begin{cases}
1, & \text{a same-class blob lies within } r_{sm}\text{ km of } f_{i,t_j} \\
0, & \text{otherwise}
\end{cases}
\tag{8b}
\end{equation}
where $\delta_j$ is simply a per-timestep flag: one interaction, one count,
nothing more elaborate. The two signals are combined into a single composite
score using a weighting constant $w_{sm}$ that converts each interaction
event into area-change-equivalent units:
\begin{equation}
V_i = \overline{\Delta A}_i + w_{sm}\, n_i^{\mathrm{sm}},
\qquad w_{sm} = 500
\tag{8}
\end{equation}
\textbf{Normalization and scoring:} Because the four metrics have incompatible units and scales, each is standardized to a $z$-score across all tracked features in the dataset before combination:
\begin{equation}
Z_{X,i} =
\frac{X_i-\mu_X}{\sigma_X},
\qquad
X \in \{D,E,V\}
\tag{8}
\end{equation}
where $\mu_X$ and $\sigma_X$ are the mean and standard deviation of metric $X$ over all tracks. The normalized metrics are combined into a single visualization-relevance score via a weighted sum:
\begin{equation}
S_i =
w_D Z_{D,i}
+
w_E Z_{E,i}
+
w_V Z_{V,i}
\tag{9}
\end{equation}

Tracks are ranked by $S_i$, and the highest-scoring features are selected for camera animation. The weights $w_L,w_D,w_E,w_V$ are treated as a visualization-oriented design choice rather than an objective measure of meteorological importance. Different weightings emphasize different kinds of ``interesting'' behaviour and their sensitivity is intended to be examined empirically.

\textbf{Camera-motion-type selection:} The same characterization that drives ranking also determines \textit{how} a selected feature should be presented. Three camera-motion archetypes are defined:

\begin{table}[htbp]
\centering
\caption{Mapping from dominant feature characteristic to camera-motion archetype.}
\label{tab:camera-motion}
\begin{tabular}{lll}
\hline
\textbf{Dominant characteristic} &
\textbf{Camera-motion type} &
\textbf{Visualization objective} \\
\hline
High travel distance &
Follow &
Emphasize the feature's geographical movement \\

Large spatial extent &
Skeleton &
Reveal the feature's spatial scale and structure \\

High shape volatility &
Orbit &
Reveal changes in the feature's morphology \\
\hline
\end{tabular}
\end{table}

This mapping ties the camera's behaviour to a measurable property of the tracked phenomenon, rather than choosing a motion independently of the data: a fast-translating cyclone earns a chase-style follow shot; a continent-spanning atmospheric river earns a shot that traces its skeleton to convey scale; a rapidly reorganizing storm earns an orbit that lets the viewer see structural change from multiple angles.

\textbf{Output interface:} For each selected feature, its trajectory (Eq. 4), the four characterization metrics (Eqs. 5--8), the composite score (Eq. 9), and the assigned motion type are serialized to an intermediate JSON file, along with supporting spatial information such as bounding boxes, needed by the camera-generation stage. This file is the sole interface to Section 4.3.


\subsection{Camera Path Generation}

Given the ranked, motion-typed feature list produced in Section 2.2, this stage synthesizes the actual Met3D camera keyframe sequences. The approach combines skeleton-based orientation detection, centroid tracking, and dynamic camera choreography to produce context-aware camera sequences: for each ranked feature, the assigned motion archetype (Table~\ref{tab:camera-motion}) is realized as one of three concrete camera behaviours --- skeleton-based spline paths for morphological inspection (\textit{skeleton}), centroid tracking for long-distance migration (\textit{follow}), and orbital rotation for shape-evolution analysis (\textit{orbit}).

\subsubsection{Evaluation Data}
Two datasets were used to develop and exercise the camera-generation stage, in addition to the 12-timestep forecast data described in Section 2. The first spans 20--27 January at 12:00 UTC; the second comprises 61 timesteps spanning 180 hours (7.5 days), from 28 January to 4 February 2026, on a global grid at approximately $0.23^{\circ}$ resolution. Both datasets were reduced to the binary AR classification field prior to camera generation; the underlying AR detection and NetCDF preparation follow the methodology of \citep{gmd2025}.

\subsubsection{Skeleton Extraction for Camera Orientation}
For features assigned the \textit{skeleton} motion type, the camera path is derived from the feature's morphological skeleton rather than its centroid. At the timestep where the feature reaches its maximum spatial extent, the AR's skeleton (Section 2.1) is re-extracted to determine its primary axis of elongation; this timestep-of-maximum-extent skeleton anchors the camera path for the full sequence.

Skeletonization was adopted on the recommendation of Met3D developers (C. Richter, personal communication), as it reliably extracts the morphological spine of irregular AR shapes. Unlike a centroid-based approach, skeletonization preserves the feature's elongation structure, enabling more accurate camera traversal along its length. An alternative based on principal component analysis (PCA) was also evaluated: initial experiments showed that a single principal axis could deviate substantially from the true AR curve whenever the feature bends irregularly. The full skeleton --- retaining all extracted points rather than a linear reduction --- was therefore used, as it provides a more faithful representation of the feature's path.

\subsubsection{Camera Offset Strategy}
To avoid the camera clipping into the feature or producing blind spots, a fixed spatial offset is applied between each waypoint and the corresponding camera position:
\begin{equation}
\varphi_{\mathrm{cam}} = \varphi_{\mathrm{AR}} - \Delta\varphi_{\mathrm{off}},
\qquad
\lambda_{\mathrm{cam}} = \lambda_{\mathrm{AR}} - \Delta\lambda_{\mathrm{off}}
\tag{10}
\end{equation}
where $\Delta\varphi_{\mathrm{off}}$ and $\Delta\lambda_{\mathrm{off}}$ are typically set to $5^{\circ}$ south and $5^{\circ}$ west of the feature, respectively. This offsets the camera away from the feature while its orientation toward the feature is maintained via the dynamic yaw computation of Section 2.3.4. The $5^{\circ}$ offset value was determined empirically through iterative testing in Met3D.

\subsubsection{Yaw Computation}
At each waypoint, the camera yaw (heading angle) is computed so that the camera points toward the next waypoint along the skeleton path:
\begin{equation}
\psi_t = -\operatorname{atan2}\!\left(\lambda_{t+1}-\lambda_t,\ \varphi_{t+1}-\varphi_t\right)
\tag{11}
\end{equation}
The negative sign in Eq.\,(11) ensures that the camera looks along the west-to-east direction of the feature's propagation, consistent with the predominant orientation of the AR skeletons observed in the evaluation data.

\subsubsection{Pitch Variation During Skeleton Traversal}
As the camera flies along the skeleton, the pitch angle is varied to emphasize the feature's vertical extent and structure: pitch is swept from a steep $60^{\circ}$ at entry to a shallow $20^{\circ}$ at exit. This progressive variation produces a cinematic ``pull-back'' effect as the camera exits the skeleton traversal, intended to sustain viewer engagement throughout the shot.

\subsubsection{Algorithm Summary}
The NetCDF probability fields and the ranked-feature JSON (Section 2.2) are combined to locate, for each selected feature, the timestep of maximum spatial extent; the feature's skeleton is extracted at that timestep; waypoints are selected along the skeleton (or centroid track, for \textit{follow} features); and the resulting waypoint sequence, together with the offset, yaw, and pitch parameters of Sections 2.3.3--2.3.5, is serialized to a Met3D-compatible XML keyframe file.

\section{Results and Evaluation}

\subsection{System Implementation}

The camera-path synthesis system was implemented in Python 3.9 using the following dependencies:
\begin{itemize}
\item \texttt{xarray} for NetCDF input/output,
\item \texttt{numpy} for numerical computations,
\item \texttt{scipy} for skeleton extraction via \texttt{scipy.ndimage},
\item \texttt{scikit-image} for morphological skeletonization, and
\item \texttt{xml.etree.ElementTree} for XML generation.
\end{itemize}

The pipeline was evaluated on the 61-time-step forecast dataset described above. The generated sequences load and execute in Met.3D and produce rendered animations of the detected atmospheric-river field.

\subsection{Validation Methodology}

Validation was carried out through iterative manual inspection in Met.3D. The process consisted of generating a candidate XML file from the Python script, loading it into Met.3D, and playing the resulting animation. The camera behaviour was then inspected to determine whether the camera followed the skeleton path correctly, whether the zoom, pitch, and yaw values were appropriate for the scene, and whether the time advancement matched the evolution of the data.

If the behaviour was not satisfactory, the parameters were manually adjusted using Met.3D's camera editor. The corrected XML was then exported and used to update the corresponding values in the Python code. The script was subsequently re-run and the resulting animation was validated again.

This iterative process was used to check visual correctness and to identify parameter ranges that produced suitable animations. The qualitative validation criteria were that the camera followed the skeleton path without major deviations, that the zoom provided good feature visibility without clipping, that the pitch and yaw produced a natural cinematic effect, and that the time evolution showed feature growth or dissipation as expected.

Two observations can be made from these results. First, the hand-authored sequences use a wider range of both zoom values (16--250) and pitch values (up to $71^{\circ}$) than the early automatically generated output, which was limited to a more conservative part of the parameter space. Second, the reference sequences achieve low reversal counts with relatively few keys. This indicates that Met.3D's interpolation contributes substantially to the smoothness of the camera motion and that using a large number of keys is not sufficient to produce smooth motion.

\subsection{Effect of Centreline Ordering}

The ordering of centreline points was found to have a strong effect on trajectory quality. A generated multi-feature sequence containing 350 keys produced 80 sharp reversals when the centreline points were ordered by longitude. Replacing this ordering with graph-order traversal of the pruned skeleton, together with ridge-based extraction, reduced the number of reversals to 3, corresponding to a reduction of approximately 96%.

A controlled test using a synthetic U-shaped feature showed the same effect. Longitude ordering produced 23 reversals, whereas graph ordering produced none.

\subsection{Effect of Camera-Offset Formulation}

The formulation used to calculate the camera offset also affected the resulting view. Sequences generated using a pitch-proportional angular offset placed the camera at displacements exceeding $50^{\circ}$ from the observed feature. In these cases, the feature left the frame partway through the animation.

Using bounded offsets of $5$--$15^{\circ}$, following the convention observed in the reference material, kept the feature within the frame throughout the animation. The results also showed that pitch magnitude alone was not the determining factor. Reference sequences successfully use pitch values of up to $71^{\circ}$ when the camera offset is appropriately bounded.

\subsection{Grammar Selection Against Feature Descriptors}

The tracked features in the test dataset differ substantially in their characteristics, supporting the use of multiple camera grammars rather than a single trajectory type. The three highest-ranked tracked features each persisted for the full 61-step window but differed in other properties. Their total travelled distance ranged from approximately 12,400 to 27,600,km, their maximum extent ranged from approximately 4000 to 11,100,km, and the number of split and merge events ranged from 11 to 59.

The feature with 59 split and merge events is poorly suited to centreline traversal because its centroid is unstable between consecutive timesteps. For this feature, an orbit around its mean position provides a more stable view of the same evolution.

\subsection{Challenges Encountered and Resolution}

\textbf{Parameter interdependence.}
Zoom, pitch, and yaw are not independent, and a poor choice of one parameter can affect the usefulness of the others. For example, a steep pitch of $60^{\circ}$ at moderate zoom (level 100) can cause clipping, while a shallow pitch of $20^{\circ}$ at close zoom (level 25) does not convey the vertical structure well. Through approximately 20 iterative test cycles in Met3D, workable parameter ranges were identified. Close zoom (level 25) requires a high pitch of $60^{\circ}$ to avoid ground clipping. Regional zoom (level 100) works best with a moderate pitch of $30$--$40^{\circ}$, while global zoom (level 250) requires a low pitch of $0$--$10^{\circ}$ to maintain geographic context. These ranges were encoded as defaults in the code, with optional overrides through the input JSON.

\textbf{Skeleton quality variability.}
Features with irregular or fragmented shapes can produce poor skeletons, including disconnected segments or spurious branches. These can result in unrealistic camera paths. This was addressed using the minimum component-size threshold introduced in Section 2.1 (50 pixels) and by interpolating waypoints across small gaps in the skeletonized region.

\textbf{Timeline non-reversibility.}
Met3D's time axis advances monotonically and cannot rewind to $t=0$ after reaching the final timestep. This prevents the full life cycles of multiple features from being shown within a single continuous animation. To address this, separate XML files are generated for each feature when the combined lifetime exceeds the available number of frames, which is 61 for the 180-hour evaluation dataset. The resulting files are loaded sequentially by the user.

\textbf{Splitting and merging.}
Some features split into multiple disconnected blobs or merge with neighbouring systems. The current skeleton-extraction step assumes a single continuous object and therefore produces multiple skeletons or fragmented paths in these cases. This issue is currently unresolved. Split and merge events are recorded in the feature metadata (Eq. 7b), but a corresponding camera-visualization strategy has not yet been developed. Multi-object tracking or temporal skeleton interpolation are identified as possible directions for future work (Section 5).

\textbf{Complex morphology.}
Highly curved or S-shaped features can produce skeletons that deviate from the intuitive centreline because of their irregular boundaries. As discussed in Section 2.3.2, a PCA-based principal-axis alternative was tested but was found to be less faithful than the full skeleton. This limitation is documented, and the skeletons are checked visually as part of the validation process described in Section 3.2.

\subsection{Design Evolution and Lessons Learned}

The design of the system developed through several iterations.

\begin{itemize}
\item \textbf{Iteration 1 --- Comprehensive coverage.}
The initial goal was to visualise all detected features in a single global-map animation. This resulted in approximately 1000 frames with jerky camera motion, making individual features difficult to follow. This showed that increasing the number of frames does not necessarily improve the animation and that the viewer needs a more focused narrative.

\item \textbf{Iteration 2 --- Sequential coverage with manual scripting.}
The second approach aimed to cover features in geographic order, from north to south, using manually authored XML. This required considerable manual work, resulted in inconsistent parameter choices, and remained unsatisfactory beyond approximately five features. This led to the need for a principled ranking system combined with automated parameter generation.

\item \textbf{Iteration 3 --- Ranked features with cinematic camera motion.}
The third approach selected the top-ranked features and applied cinematic techniques, including zoom, pitch, and pause-and-spin. This was inspired by NASA's atmospheric-river visualisations \citep{nasa-climate}, in which time is paused to highlight important features. The resulting animations were substantially more engaging, and viewers could follow feature evolution and morphology more easily. This showed that meteorological visualisation can benefit from established cinematic storytelling principles.

\item \textbf{Iteration 4 --- Current status.}
The current system automatically generates cinematic sequences using dynamic camera paths tied to feature morphology through the skeleton (Section 2.3.2), ranked feature selection based on distance, extent, and change (Section 2.2), and iterative validation (Section 3.2). The resulting process produces production-quality animations.
\end{itemize}

\subsection{Limitations}

The current implementation has several limitations:
\begin{enumerate}
\item It assumes a single continuous feature object and cannot yet handle splitting or merging events during camera-path generation.
\item Manual validation of the generated XML is still required, and no automated visual-quality score is currently available.
\item Some pitch and zoom values are hardcoded, which limits user customisation beyond the JSON override mechanism.
\end{enumerate}
